Why Does This Code Take So Long?

Algorithm complexity & hashing — free lesson · takes about 9 minutes to read

1.Why do we even talk about "complexity"?

Imagine you're looking for your best friend's phone number. If it's the very first contact pinned at the top, you find it instantly — no matter how many thousand contacts you have. That's fast, always.

Now imagine your contacts aren't sorted at all, and you have to scroll past every single name until you spot theirs. If you have 50 contacts, that's mildly annoying. If you have 50,000, that's a real wait — and it keeps getting worse as your contact list grows.

Complexity analysis is just a way of describing "how much worse does this get as the input grows." Some approaches barely slow down. Others get dramatically slower. That's what Big-O notation measures.

2.Asymptotic Notations (the growth-rate labels)

Very high — asked almost every semester
Now in exam language — the common growth rates:
  • O(1) — Constant: same time regardless of input size (pinned contact).
  • O(log n) — Logarithmic: time grows very slowly as input grows (looking up a word in a dictionary — you skip half the remaining pages each guess).
  • O(n) — Linear: time grows directly with input size (scrolling through an unsorted contact list).
  • O(n²) — Quadratic: time grows much faster — checking every pair of students against each other for matching answers.
Draw a rough version of this in your exam when asked to compare growth rates — examiners look for the shape, not exact math.

3.Hashing — jumping straight to the answer

Imagine a library with a million books, but instead of searching shelf by shelf, every book's title gets fed into a formula that instantly spits out "Shelf number 482." You walk straight there — no searching at all.

That formula is a hash function, and the shelf numbers are a hash table. Instead of scanning through data one item at a time, hashing converts a key directly into the exact location where it lives.

Now in exam language:

Hashing is a technique that converts a key into an array index using a hash function, allowing near-instant (average O(1)) insertion and lookup — instead of scanning through every element like a plain list would.

Real example

Your phone's contact search bar doesn't scroll through every name when you type — it uses hashing internally to jump close to the matching entries almost instantly, even with thousands of contacts.

4.Collisions — when two keys land on the same shelf

Sometimes two completely different book titles both hash to "Shelf 482." That's a collision — two keys landing in the same spot. There are two common ways to handle it:

Chaining: just let both books sit on the same shelf, one behind the other, like a small stack. When you arrive at Shelf 482, you check the short stack to find the exact one you want.

Open addressing (linear probing): if Shelf 482 is full, the librarian has a rule — "if taken, try the next shelf, then the next" — until an empty spot is found.

Now in exam language — collision resolution techniques:
  • Separate Chaining: each hash table slot holds a linked list of all elements that hashed to it.
  • Linear Probing: on collision, search sequentially for the next empty slot.
  • Quadratic Probing / Double Hashing: variations that jump around more cleverly to reduce clustering.

5.Practice Question (try it yourself)

Explain any two collision resolution techniques in hashing with a suitable example. 10 marks

Tip: draw a small hash table (5-6 slots), show two keys landing on the same slot, then show how chaining vs. linear probing each resolve it differently — visual answers score higher than definitions alone.
