Unit 2 — Relational Model & Basic SQL

Primary Key vs Foreign Key vs Candidate Key

Every student in your college has a unique roll number — that's a bit like a Primary Key. No two students share one, and it's how the office identifies you.

Now imagine the library keeps a record of "which roll number borrowed which book." That roll number sitting inside the library's table, pointing back to the student table, is a Foreign Key — it links one table to another.

A Candidate Key is any column that *could* have been chosen as the primary key (like your roll number OR your Aadhaar number — either uniquely identifies you, but only one gets picked as "the" key).

Now in exam language:

Primary Key: a column (or set of columns) that uniquely identifies each row in a table, and cannot be NULL.
Candidate Key: any minimal set of columns that could uniquely identify a row — one of these is chosen as the primary key.
Foreign Key: a column in one table that refers to the primary key of another table, used to link related data.

GROUP BY and HAVING

Imagine sorting your class into groups by branch — CSE students in one pile, ECE in another. That's GROUP BY. Now if you only want to see groups with more than 40 students, that filter-after-grouping is HAVING.

Now in exam language:

GROUP BY groups rows sharing a value into summary rows, usually used with aggregate functions (COUNT, SUM, AVG). HAVING filters those grouped results — unlike WHERE, which filters rows before grouping.

Write a query to find departments with more than 5 employees, using GROUP BY and HAVING.5 marks

Tip: write the SELECT ... FROM ... GROUP BY ... HAVING skeleton first, then fill in the condition — examiners give partial marks for correct structure even if the condition is off.

Unit 3 — ER Model & Advanced SQL

Specialization & Generalization in ER Diagrams

Think of "Vehicle" as a broad category. A Car and a Bike are both vehicles, but each has its own extra details — a car has "number of doors," a bike doesn't. Splitting "Vehicle" into more specific types like Car and Bike is called specialization.

Generalization is the reverse — you notice Car and Bike share common features (both have a registration number, both have an owner), so you pull those shared features up into one general "Vehicle" entity.

Now in exam language:

Specialization: top-down process of defining subclasses of an entity based on distinguishing characteristics. Generalization: bottom-up process of combining common attributes of multiple entities into a single superclass.

Joins — the visual way to remember them

Imagine two friend groups sitting in two different lines. An INNER JOIN only keeps people who have a friend in the other line. A LEFT JOIN keeps everyone from the first line — friend or not. A RIGHT JOIN does the same but keeps everyone from the second line. A FULL OUTER JOIN keeps everyone from both lines, matched or not.

Now in exam language:

Joins combine rows from two or more tables based on a related column. The type of join determines which unmatched rows (if any) are still included in the result.

Explain the difference between INNER JOIN and LEFT JOIN with an example.10 marks

Tip: always draw two small sample tables (3-4 rows each) and show the actual output table — visual answers score noticeably higher than pure definitions.

Unit 4 — Normalization & Transactions

Normalization — the numerical everyone loses marks on

Imagine one giant table trying to store a student's name, their branch, AND every single subject they're taking, all in one row that keeps repeating. If a subject's credit count changes, you'd have to update it in a hundred different rows. Normalization is just the process of splitting this messy giant table into smaller, cleaner ones so you only ever have to update information in one place.

ACID Properties of a Transaction

Imagine transferring money to a friend via UPI. Either the full transfer happens, or none of it does — you'd never want money to leave your account without reaching your friend's. That "all or nothing" promise is what ACID properties guarantee for every database transaction.

Now in exam language:
  • Atomicity: a transaction is all-or-nothing — either fully completes or fully rolls back.
  • Consistency: a transaction takes the database from one valid state to another, never breaking rules.
  • Isolation: concurrent transactions don't interfere with each other's intermediate results.
  • Durability: once committed, changes survive even a system crash.

Unit 5 — Indexing & Database Tuning

Why indexes exist (and B+ Trees)

Imagine looking for one word in a 500-page textbook with no index at the back — you'd have to flip through every single page. Now imagine the book has an index page listing words alphabetically with page numbers. That's exactly what a database index does — it lets the system jump straight to the right row instead of scanning the whole table.

A B+ Tree is just a smart, organized version of that index — like a index that's itself split into smaller sub-indexes so even a huge book stays fast to search.

Now in exam language:

A B+ Tree is a balanced tree data structure used for indexing, where all actual data pointers are stored only at the leaf nodes, and internal nodes only guide the search — keeping search, insert, and delete operations efficient at O(log n).

Primary vs Secondary Indexing

A primary index is like a phone book sorted by name — the data itself is physically stored in that sorted order. A secondary index is like a separate list sorted by phone number instead — the actual data isn't rearranged, just a pointer list is added.

Differentiate between primary and secondary indexing with examples.5 marks

Tip: mention that a table can have only ONE primary index (since data can only be physically sorted one way) but MULTIPLE secondary indexes.
